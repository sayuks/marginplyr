# Backend API audit

Date: 2026-07-27

## Scope

This audit reviews `R/` for code that can be made more idiomatic, efficient,
or resilient by using the public APIs of dplyr, dbplyr, dtplyr, tidyselect,
rlang, and Arrow. It focuses on:

- package-private S3 generics and backend-specific methods;
- zero-row `collect()` calls;
- direct access to backend classes or internal fields;
- tidyselect and `across()` handling;
- SQL construction and quoting.

No package implementation was changed during this audit. The recently
simplified `get_col_names()` is used as the comparison point: select through
the backend's public `select()` method, then inspect variables through
`tbl_vars()`.

## Executive summary

The current design is generally sound. In particular,
`tidyselect::eval_select()`, `dplyr::group_vars()`,
`dbplyr::remote_con()`, and `dbplyr::sql_dialect()` are appropriate public
extension APIs. The portable `UNION ALL` strategy and the native
`GROUPING SETS` strategy both have legitimate reasons to exist.

There are, however, five changes worth prioritising:

1. Fix temporary-name reservation in the union and native SQL adapters.
   `colnames()` loses dtplyr/Arrow query names, and unnamed `across()` outputs
   are not currently reserved. This is a correctness issue, not just cleanup.
2. Replace superseded dbplyr SQL builders (`build_sql()` and `sql_call2()`)
   with `sql_glue2()`.
3. Replace one margin-label collision query per dimension with one
   column-wise aggregation.
4. Use Arrow's public schema metadata instead of executing a zero-row query.
5. Reuse the zero-row typed proxy already collected for tidyselect instead of
   collecting the same schema a second time.

The direct mutation of `result$lazy_query` should also be moved to a custom
lazy-query object created by dbplyr's exported `lazy_query()` constructor. It
is the highest long-term compatibility risk, but the refactor itself deserves
careful integration testing.

## Findings

### 1. Internal-name reservation has two correctness holes

**Priority:** P0
**Importance:** High
**Confidence:** High
**Compatibility risk of change:** Low

Locations:

- `R/grouping-adapter-union.R:9`
- `R/grouping-adapter-union.R:41`
- `R/grouping_sets.R:14-15`
- `R/grouping_sets.R:65-77`
- `R/internal-names.R:1-19`
- `R/summary-selections.R:251`

`colnames()` returns the expected values for local data frames, dbplyr tables,
Arrow `Table`s, and Arrow `Dataset`s. It returns `NULL` for both a
`dtplyr_step` and an `arrow_dplyr_query`, while `dplyr::tbl_vars()` returns
their projected variables. This was reproduced with dtplyr 1.3.3 and Arrow
25.0.0.

The two calls in `summarize_margin_union()` are consequential:

- the first can fail to reserve an input name such as
  `..marginplyr_key_1`, allowing an internal temporary name to collide with
  user data;
- the second can fail to detect that a summary result overwrote a grouping
  column.

An input column literally named `..marginplyr_key_1` produced a dtplyr
collection/type error in a focused reproduction. Use the existing
backend-safe helper instead:

```r
data_vars <- get_col_names(.data, dplyr::everything())
result_vars <- get_col_names(result, dplyr::everything())
```

`dplyr::tbl_vars()` is the public API for listing variables supplied by a
`tbl`; it returns all variables and carries grouping variables as metadata
([dplyr `tbl_vars()` reference](https://dplyr.tidyverse.org/reference/tbl_vars.html)).
As with the current `get_col_names()`, selecting first is necessary because
raw Arrow `Table` and `Dataset` objects do not themselves provide the same
`tbl_vars()` method as an Arrow dplyr query.

There is a second, independent collision path. `names(dots)` does not contain
columns generated by an unnamed data-frame summary such as:

```r
dplyr::across(value, mean, .names = "..marginplyr_key_1")
```

That output collides with a temporary union key on local, dtplyr, and Arrow
backends. The analogous name `..marginplyr_grouping_1` collides with a native
SQL grouping flag and currently produces a cryptic dbplyr error.

The main summary function already computes `known_summary_output_names()`.
Pass those names into both adapters and include them in `used_names` together
with:

- input variables from `get_col_names()`;
- explicitly named summary dots;
- any other reserved output names.

Then generate both union keys and native grouping flags through the shared
`new_margin_internal_names()` helper. Add direct regression tests using input
and summary-output names that exactly match every internal prefix.

`summary_all_of_expr()` should likewise use the already known data-variable
vector, or a backend-safe helper, rather than indexing `colnames(data_proxy)`.
This is less urgent because the current proxy is usually a local data frame
for Arrow and dtplyr, but using one metadata convention avoids another
backend-specific assumption.

### 2. SQL construction uses APIs that dbplyr has superseded

**Priority:** P1
**Importance:** High
**Confidence:** High
**Compatibility risk of change:** Low to medium

Locations:

- `R/factor.R:46-58`
- `R/grouping-context.R:202-229`
- `R/grouping_sets.R:97-125`

The implementation currently combines `ident()`, `escape()`, `sql_vector()`,
`build_sql()`, and `sql_call2()`.

dbplyr now marks `build_sql()` as superseded by `sql_glue2()`
([dbplyr `build_sql()` reference](https://dbplyr.tidyverse.org/reference/build_sql.html)).
The current dbplyr help also marks `sql_call2()` as superseded. More
importantly, dbplyr describes `sql_glue()` and `sql_glue2()` as tools designed
for dbplyr extenders, with `sql_glue2()` intended for code that has an explicit
connection. Its `{.id x}` marker safely quotes identifiers, ordinary `{x}`
escapes values, and `*` adds parentheses around vectors
([dbplyr `sql_glue2()` reference](https://dbplyr.tidyverse.org/reference/sql_glue.html)).
The official backend-development article explicitly recommends
`sql_glue2()` when generating custom SQL
([dbplyr backend guide](https://dbplyr.tidyverse.org/articles/new-backend.html#building-sql-strings)).

Representative replacements are:

```r
dbplyr::sql_glue2(con, "GROUPING({.id var})")

dbplyr::sql_glue2(
  con,
  "CAST({.id col} AS ENUM {new_levels*})"
)

dbplyr::sql_glue2(con, "{.id vars*}")
```

With dbplyr 2.6.0, these forms were verified to quote non-syntactic
identifiers, embedded apostrophes, and empty grouping sets correctly:

```sql
GROUPING("odd name")
CAST("odd name" AS ENUM ('Total', 'O''Brien'))
()
```

For the outer `GROUPING SETS (...)` string and the arithmetic expression used
by `grouping_id()`, first combine already escaped SQL fragments into one
string, then interpolate that string with `{.sql ...}`. `sql_glue2()` requires
the value of a `.sql` marker to be a single string.

The compatibility risk is mostly snapshot churn from whitespace or quoting,
not a semantic change. Retain SQL-render tests for every simulator and the
live DuckDB identifier/factor tests.

### 3. Native grouping sets are attached by mutating an existing dbplyr query

**Priority:** P1
**Importance:** High for long-term compatibility
**Confidence:** High that a public constructor is preferable; medium on the
final refactor shape
**Compatibility risk of change:** Medium to high

Location: `R/grouping_sets.R:38-42`

The code currently adds an arbitrary field to the existing
`lazy_select_query` and prepends a class directly:

```r
result$lazy_query$marginplyr_grouping_sets <- plan$sets
class(result$lazy_query) <- c(
  "lazy_grouping_sets_query",
  class(result$lazy_query)
)
```

dbplyr documents that a `tbl_lazy` contains a connection and a `lazy_query`,
and that verbs wrap existing lazy queries with new lazy-query nodes
([dbplyr backend guide](https://dbplyr.tidyverse.org/articles/new-backend.html#behind-the-scenes)).
It also exports `lazy_query()` specifically to construct custom lazy query
objects, and `sql_build()` as the generic that converts them to query objects
([dbplyr SQL build reference](https://dbplyr.tidyverse.org/reference/sql_build.html)).
This is still a deliberately cautious recommendation: dbplyr labels its lazy
operation API as very new and likely to evolve
([dbplyr lazy operations reference](https://dbplyr.tidyverse.org/reference/lazy_ops.html)).

Prefer an explicit wrapper:

```r
result$lazy_query <- dbplyr::lazy_query(
  "grouping_sets",
  x = result$lazy_query,
  grouping_sets = plan$sets,
  group_vars = character()
)
```

Then provide:

- an `op_vars.lazy_grouping_sets_query()` S3 method for the exported
  `dbplyr::op_vars()` generic, delegating to `op$x`;
- the existing `sql_build.lazy_grouping_sets_query()`, building `op$x` and
  replacing the built select query's `group_by`.

A small prototype with dbplyr 2.6.0 rendered native `GROUPING SETS`, preserved
`tbl_vars()` and `group_vars()`, and supported a downstream `mutate()` by
placing the custom query in a subquery.

This does not remove every dependency on dbplyr's query representation:
`sql_build()` must still return a select query whose `group_by` can be
replaced. It does, however, stop pretending that a normal
`lazy_select_query` has an extra field and makes the extension boundary
explicit through dbplyr's constructor and generics.

Required regression coverage:

- `sql_render()` for all supported native dialects;
- downstream `select()`, `mutate()`, `filter()`, `arrange()`, and
  `collect()`;
- `tbl_vars()` and `group_vars()` before and after downstream verbs;
- duplicate grouping sets and the empty grouping set.

An independent, lower-risk optimisation is available in the same adapter.
The internal `GROUPING(...)` flag columns created at
`R/grouping_sets.R:14-26` are used only to replace omitted dimensions with a
non-`NULL` display label. When `.margin_label = NULL`, grouping identity
helpers in user summaries are already rewritten directly to their own
`GROUPING(...)` expressions, so the extra internal flags can be skipped
entirely instead of generated and immediately dropped.

### 4. Margin-label collision detection performs one query per dimension

**Priority:** P1
**Importance:** High for remote data
**Confidence:** High
**Compatibility risk of change:** Medium

Location: `R/summarize_with_margins.R:400-420`

`assert_margin_name()` currently filters, summarises, and collects once for
each grouping dimension. With `p` dimensions, this creates `p` lazy queries
and `p` backend round trips.

Construct one named check expression per column, then inject all checks into
one `summarise()`:

```r
checks <- lapply(col_names, function(col) {
  column <- rlang::sym(col)
  if (is.na(margin_name)) {
    rlang::expr(any(is.na(!!column), na.rm = TRUE))
  } else {
    rlang::expr(any(!!column == !!margin_name, na.rm = TRUE))
  }
})
names(checks) <- col_names

found <- data |>
  dplyr::summarise(!!!checks) |>
  dplyr::collect()
```

The one-query form was verified with local data, dtplyr 1.3.3, Arrow 25.0.0,
and DuckDB 1.5.4.3, for both a character label and `NA_character_`. Arrow's
current supported-function list includes `summarise()`, `any()`, `is.na()`,
and equality operations
([Arrow dplyr function reference](https://arrow.apache.org/docs/r/reference/acero.html)).
In a directional live-DuckDB check with 12 columns and 10 repetitions, the
old per-column approach took about 0.599 seconds and the one-query approach
about 0.163 seconds (approximately 3.67 times faster). This measures
round-trip overhead in one environment, not package-wide throughput.

Use symbol injection rather than `.data[[col]]` inside the aggregate
expression. A focused Arrow reproduction returned an incorrect aggregate for
the latter form, while injecting `rlang::sym(col)` produced the correct query
and result across the verified backends. dplyr's programming guidance
documents tidy evaluation and injection for indirection in data-masking verbs
([dplyr programming vignette](https://dplyr.tidyverse.org/articles/programming.html)).

Also avoid a function stored in a local variable. dtplyr and dbplyr translate
the expression tree; an opaque call such as `f(a)` can be sent to the backend
as an unknown function.

Tests should cover all-missing columns, empty inputs, `NA` labels, factor
columns, non-syntactic names, and generic PostgreSQL SQL rendering.

### 5. Arrow can provide the typed proxy directly from schema metadata

**Priority:** P1
**Importance:** Medium to high
**Confidence:** High
**Compatibility risk of change:** Low to medium

Location: `R/grouping-plan.R:313-319`

For Arrow objects, the current `collect(head(.data, 0))` is not required to
obtain column names and R-compatible prototype types:

```r
proxy <- as.data.frame(arrow::schema(.data))
```

Arrow documents `schema()` as the public function for extracting a schema from
an object ([Arrow `schema()` reference](https://arrow.apache.org/docs/r/reference/schema.html)).
With Arrow 25.0.0, `schema()` and `as.data.frame()` produced a typed zero-row
tibble for:

- `Table`;
- `Dataset`;
- `arrow_dplyr_query`, including projected and computed columns.

This avoids executing the Arrow query plan solely to evaluate tidyselect
predicates or obtain missing-value prototypes. In a 100-iteration focused
measurement on the current Arrow query, schema conversion was about 5.35
times faster than `collect(head(query, 0))`; treat that number as directional,
not a package benchmark.

One detail needs explicit regression coverage: converting an Arrow dictionary
schema to a data frame preserves the factor and ordered attributes but returns
empty levels, whereas `collect(head(raw_table, 0))` can retain the source
levels. marginplyr already sets `can_restore_factors = FALSE` for Arrow. A
focused margin-union prototype with `.margin_label = NULL` and a typed missing
value still retained the original detail levels after `union_all()` on Arrow
25.0.0. Nevertheless, factor/dictionary columns, ordered factors, computed
queries, and `.margin_label = NULL` should all be regression-tested before
using the schema proxy.

There is no equivalent universal public API that returns R prototypes for an
arbitrary dbplyr query without executing it. Keep a zero-row query where the
backend genuinely needs one.

### 6. The typed zero-row proxy is collected twice

**Priority:** P1
**Importance:** Medium to high
**Confidence:** High
**Compatibility risk of change:** Low

Locations:

- `R/grouping-plan.R:313-319`
- `R/margin-label.R:14-46`
- callers in `summarize_with_margins()`, `expand_with_margins()`, and
  `nest_with_margins()`

For dtplyr, Arrow, and DuckDB, `grouping_selection_proxy()` currently collects
`head(..., 0)` so tidyselect predicates such as `where(is.character)` can see
R column types. Later in the same operation, `margin_column_info()` collects
the same zero-row result again to derive prototypes and factor levels.

For dtplyr and DuckDB, the first collection is justified. tidyselect documents that
`eval_select()` evaluates against a data-like proxy and only permits
predicates when that proxy supports them
([tidyselect `eval_select()` reference](https://tidyselect.r-lib.org/reference/eval_select.html)).
dtplyr explicitly documents that predicate selection such as `where()` is not
supported on lazy steps
([dtplyr changelog](https://github.com/tidyverse/dtplyr/blob/main/NEWS.md)).
Collecting a zero-row typed proxy is therefore an intentional compatibility
feature on those backends. Arrow should use the schema path described above.

For every backend, the second collection is unnecessary. Pass the
already-created proxy into
`margin_column_info()`, and use it when it is a local data frame. Generic SQL
backends for which schema reading is disabled can keep the current no-schema
path.

`collect()` is the public generic that retrieves a lazy result locally
([dplyr `collect()` reference](https://dplyr.tidyverse.org/reference/compute.html)).
Even with zero rows, eliminating a duplicate call avoids a second backend
translation/execution boundary.

### 7. Several private S3 generics can become ordinary backend-neutral helpers

**Priority:** P2
**Importance:** Medium
**Confidence:** High for relocation; medium for Arrow `.by` consolidation
**Compatibility risk of change:** Low to medium

Locations:

- `R/summarize_with_margins.R:356-398` (`summarize_impl`)
- `R/summarize_with_margins.R:445-497` (relocation helpers)
- `R/summarize_with_margins.R:499-513` (`arrange_impl`)
- corresponding registrations in `NAMESPACE`

The `.margin_pairs` argument of `summarize_impl()` is always passed as an
empty list and has no other caller. Remove it as dead plumbing when
consolidating this helper.

#### Relocation

Every `relocate_before_union_all()` method can be represented by the Arrow
method's existing expression:

```r
dplyr::select(
  .data,
  dplyr::all_of(cols_first),
  dplyr::everything()
)
```

`select()` is supported by local data frames, dbplyr, dtplyr, and Arrow
([dplyr `select()` reference](https://dplyr.tidyverse.org/reference/select.html);
[Arrow supported verbs](https://arrow.apache.org/docs/r/reference/acero.html)).
This removes five S3 registrations.

The post-processing relocation can use the same character-vector interface.
Current Arrow supports `relocate()` as a public dplyr method, including after
`union_all()`, but using `select(all_of(cols), everything())` is enough for
marginplyr's fixed "keys first" requirement and has the broadest backend
coverage. dplyr documents `relocate()` as a generic for local and lazy data
frames ([dplyr `relocate()` reference](https://dplyr.tidyverse.org/reference/relocate.html)).

#### Arrangement

Arrow 25.0.0 rejects `arrange(pick(...))`, which explains the current Arrow
method, but accepts direct column expressions. Resolve the sort columns once
to a character vector, then splice symbols:

```r
dplyr::arrange(.data, !!!rlang::syms(sort_cols))
```

This worked unchanged for local, dbplyr, dtplyr, and Arrow objects.
`arrange()` officially accepts variables or functions of variables through
its data-masking interface
([dplyr `arrange()` reference](https://dplyr.tidyverse.org/reference/arrange.html)).
This removes the need for a marginplyr S3 generic without depending on Arrow's
unsupported interpretation of `pick()` inside `arrange()`.

#### Summary

Arrow supports per-operation `.by` from version 13.0.0, and Arrow 25.0.0
successfully
executed:

```r
dplyr::summarise(query, n = dplyr::n(), .by = group)
```

dtplyr officially exposes `.by` on its summarise method
([dtplyr summarise reference](https://dtplyr.tidyverse.org/reference/summarise.dtplyr_step.html)),
and dbplyr and local dplyr also support the existing default implementation.
Arrow's official function index lists `summarise()` as a supported lazy verb
([Arrow supported verbs](https://arrow.apache.org/docs/r/reference/acero.html)).
Arrow's official changelog records `.by` support in 13.0.0
([Arrow changelog](https://arrow.apache.org/docs/r/news/index.html)).

Consequently, `summarize_impl()` can probably become one ordinary call using
`.by = all_of(.by)`. Because Arrow is only in `Suggests` with no minimum
version, the recommended package policy is:

- declare `arrow (>= 13.0.0)` in `Suggests`;
- use the single `.by` implementation;
- keep backend tests on the current Arrow release.

dtplyr is also listed without a minimum version, while marginplyr depends on
per-operation `.by`. dtplyr added `.by` in 1.3.0, then fixed non-standard
grouping names and `.data[[...]]` handling in 1.3.2; 1.3.3 carries the latest
dplyr compatibility fix
([dtplyr changelog](https://github.com/tidyverse/dtplyr/blob/main/NEWS.md)).
Use at least `dtplyr (>= 1.3.2)`, or `>= 1.3.3` if the package explicitly
targets current dplyr 1.2 behaviour.

### 8. `nest_by_with_margins()` can call the public `collect()` generic
unconditionally

**Priority:** P2
**Importance:** Low to medium
**Confidence:** High
**Compatibility risk of change:** Low

Location: `R/nest_by_with_margins.R:118-120`

The current code checks the concrete `dtplyr_step` class before collecting.
`dplyr::collect()` has a data-frame method that returns local data unchanged,
as well as backend methods for lazy objects. dplyr documents both local and
lazy data frames as accepted inputs
([dplyr `collect()` reference](https://dplyr.tidyverse.org/reference/compute.html)).

Since `nest_by_with_margins()` has already restricted its input to local data
frames and dtplyr steps, this can be:

```r
result <- dplyr::collect(result)
```

This expresses the actual invariant—`rowwise()` needs a local result—without
asking which backend produced it.

### 9. Retain the summary-selection rewrite and dtplyr name normalization

**Priority:** Keep; add regression coverage
**Importance:** High for compatibility
**Confidence:** High
**Compatibility risk of removal:** High

Locations:

- `R/summarize_with_margins.R:288-296`
- `R/summary-selections.R:57-210`

The general selection rewrite is justified: marginplyr must exclude every
grouping dimension from `across()`, `if_any()`, `if_all()`, and `pick()`, and
must turn predicate selection evaluated on the typed proxy into an explicit
`all_of()` selection that lazy backends understand.

The dtplyr-only `normalize_across_names` branch goes further: for the supported
single-function case, it resolves `.names` itself and turns the result into a
named explicit selection. Although an isolated dtplyr call can handle many
`.names` forms, a focused test through marginplyr's full selection rewrite
showed that setting `normalize_across_names = FALSE` changed the expected
`n_value` output back to `value`. The workaround is therefore still active,
not obsolete.

dtplyr's official summarise documentation supports `across()` output, and its
method has `.by`
([dtplyr summarise reference](https://dtplyr.tidyverse.org/reference/summarise.dtplyr_step.html)).
dplyr owns the general `.names` and `.unpack` semantics
([dplyr `across()` reference](https://dplyr.tidyverse.org/reference/across.html)).

Keep the current narrow dtplyr normalization until an upstream change or a
different explicit-selection representation makes it unnecessary. Tests
should cover:

- one and multiple functions;
- named and unnamed function lists;
- `.names` with `{.col}` and `{.fn}`;
- `.unpack`;
- named tidyselect inputs;
- grouping-key and internal-name collisions.

The separate `known_across_output_names()` logic still has a purpose: it
performs marginplyr's preflight check that summaries cannot overwrite visible
grouping keys and, after finding 1, must also reserve generated output names
against internal columns. There is no public dplyr API that expands
`across()` names without evaluating the summary, so that conservative
analysis should remain and be heavily tested.

### 10. Use rlang's call-inspection helpers consistently

**Priority:** P3
**Importance:** Low
**Confidence:** High
**Compatibility risk of change:** Low

Locations:

- `R/grouping-plan.R:260-290`
- `R/grouping-context.R:132-154`

These functions manually inspect `expr[[1]]`, `::`, and `:::` calls. The same
package already uses `rlang::call_name()` and `rlang::call_ns()` in
`summary-selections.R`.

rlang documents `call_name()` and `call_ns()` specifically for extracting the
function and namespace from simple calls and returning `NULL` for complex
calls
([rlang call inspection reference](https://rlang.r-lib.org/reference/call_name.html)).
Using them consistently would shorten constructor/helper detection and reduce
hand-written AST indexing. This is cleanup only; the current implementation is
not inefficient.

### 11. `group_by_drop_default()` can replace one concrete class guard

**Priority:** P3
**Importance:** Low
**Confidence:** High
**Compatibility risk of change:** Low

Location: `R/grouped-input.R:11-18`

The current `.drop = FALSE` guard first requires
`inherits(.data, "grouped_df")` and then calls
`dplyr::group_by_drop_default()`. The latter is already the public generic for
this question and returns `TRUE` by default for objects without persistent
empty groups
([dplyr `group_by_drop_default()` reference](https://dplyr.tidyverse.org/reference/group_by_drop_default.html)).

After the earlier rowwise rejection, the condition can be reduced to:

```r
if (!dplyr::group_by_drop_default(.data)) {
  # existing error
}
```

This was checked on ungrouped and grouped local data, `.drop = FALSE` and
`.drop = TRUE`, dbplyr, dtplyr, and Arrow inputs. Keep the `rowwise_df` class
check: dplyr documents `rowwise_df` as distinct from `grouped_df`, and no
corresponding exported rowwise predicate covers this use
([dplyr `rowwise()` reference](https://dplyr.tidyverse.org/reference/rowwise.html)).

### 12. Prefer public Arrow leaf classes over the unexported superclass

**Priority:** P3
**Importance:** Low to medium
**Confidence:** Medium
**Compatibility risk of change:** Medium

Locations:

- `R/grouping-backend.R:4-7`
- Arrow-specific S3 registrations in `NAMESPACE`

`ArrowTabular` is a useful common superclass, but Arrow does not export it as
a public constructor/API in its namespace. After removing the relocation and
summary shims, their `ArrowTabular` S3 registrations disappear naturally.
For the remaining capability classification, consider spelling out the
documented/user-visible leaf types—`Table`, `RecordBatch`, `Dataset`, and
`arrow_dplyr_query`—rather than treating the unexported superclass as a
permanent contract. Arrow's namespace is the primary record of what it
exports
([Arrow `NAMESPACE`](https://github.com/apache/arrow/blob/main/r/NAMESPACE)).

This is not urgent: the existing checks are centralised in one adapter and
are preferable to accessing Arrow query fields. Before changing them, test
`Table`, `RecordBatch`, `Dataset`, computed queries, and the intentionally
rejected `RecordBatchReader`.

## APIs that should remain

### `tidyselect::eval_select()`

This is not an unnecessary reimplementation. `eval_select()` is the official
package API for evaluating defused tidyselect expressions and is explicitly
described as the engine behind `dplyr::select()`
([tidyselect reference](https://tidyselect.r-lib.org/reference/eval_select.html)).
marginplyr needs the returned positions and names while compiling grouping
families, so direct use is appropriate.

### The typed selection proxy

Do not remove the typed proxy merely to avoid work. It supplies R types for
`where()` and other predicates on backends that cannot evaluate predicate
selection lazily. Build it from `arrow::schema()` for Arrow; where a backend
has no equivalent schema API, collect zero rows once and reuse that result.

`dplyr::tbl_ptype()` is conceptually related but is not a drop-in
replacement. dplyr describes it as a prototype hook for type-based selection
([dplyr `tbl_ptype()` reference](https://dplyr.tidyverse.org/reference/tbl_ptype.html)),
but its current default method collects up to 100 rows for `tbl_lazy` and
there are no specialised dtplyr or Arrow methods. The explicit Arrow-schema
and zero-row backend paths are both cheaper and more predictable for this
package.

### `dbplyr::remote_con()` and `dbplyr::sql_dialect()`

Both are exported abstractions. dbplyr's current backend guide recommends
dialect classes for SQL behaviour because the same dialect can be shared by
DBI, ODBC, JDBC, or ADBC connections
([dbplyr backend guide](https://dbplyr.tidyverse.org/articles/new-backend.html#define-a-dialect)).
The current DuckDB/PostgreSQL capability detection follows that direction and
also retains a connection-class fallback for DuckDB.

### Backend class checks where no capability generic exists

The backend checks in `grouping_backend()` describe capabilities that dplyr
does not expose through one universal generic, such as whether marginplyr may
construct a typed selection proxy or restore factor levels. Replacing these
checks with calls to backend internal fields would be worse. Keep the checks
concentrated in the adapter and covered by backend tests, while preferring
public leaf classes over `ArrowTabular` as described above.

### Custom summary-selection analysis

The AST walk around `across()` and `pick()` is substantial, but it enforces
marginplyr-specific semantics:

- grouping dimensions are excluded from column-wise summaries across every
  grouping-set branch;
- predicate selections are resolved once against a typed proxy;
- summary outputs are checked before they can overwrite visible group keys.

There is no public dplyr API that exposes its fully expanded summary
expressions without evaluating the summary. Keep this logic and the currently
necessary dtplyr name normalization, while using official rlang call helpers
where practical.

## Recommended implementation order

1. Fix internal-name reservation using backend-safe variables plus known
   summary output names, and unify flag/key name generation.
2. Convert custom SQL construction to `sql_glue2()`.
3. Batch margin-label collision checks into one aggregation.
4. Build the Arrow typed proxy from `schema()` and reuse one proxy everywhere.
5. Reuse the typed zero-row proxy for margin column information on other
   backends.
6. Refactor native grouping sets around `lazy_query()` and `op_vars()`.
7. Collapse relocation/arrangement shims into ordinary helpers.
8. Document minimum Arrow/dtplyr versions, remove the obsolete Arrow `.by`
   shim, and retain the verified dtplyr `.names` workaround.
9. Skip native display-label flags when `.margin_label = NULL`.
10. Apply the smaller unconditional-`collect()`, `group_by_drop_default()`,
    and rlang call-inspection cleanups.
