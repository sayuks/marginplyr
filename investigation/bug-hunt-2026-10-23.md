# 広範囲バグハントの結果

Investigated: 2026-10-23
Source: `0e3f1dcca46f4d51d4d99cd200cf73540c96133d`

この調査では、公開APIの意味論、式の書き換え、型付きメタデータ、
ローカル・lazyバックエンドの差、特殊名、空入力、構成比、診断、
パッケージのビルドを調べた。SQL監査記録機能と、その調整中の仕様は対象外とした。
実装と既存テストは変更していない。

結果は**7件の独立した実行時の根因**と、**1件のローカルビルドの除外漏れ**だった。
以下の優先度は修正の提案順位であり、再現頻度の統計ではない。

| 番号 | 優先度 | 問題 | 主な影響 |
|---|---|---|---|
| 1 | 高 | 外側の式書き換えが内側の別処理へ侵入 | Grouping bitや内側の列選択が静かに変わる |
| 2 | 高 | dtplyrのゼロ行proxyが実データの型・levelsと異なる | 結果の実値がNAになる、列の誤選択、衝突の見逃し |

| 4 | 中 | eager branch結合が有効な列名を修復する | 列の改名、dimension・固定キー・idで内部エラー |
| 5 | 中 | SQL shareの固定キー改名がpronounを評価する | `.env` / `.data`固定キーでParent/Total shareが失敗 |

## 1. 内側の独立した処理に外側の書き換えが適用された

再現:
[01-nested-operation.R](bug-hunt-2026-10-23/01-nested-operation.R)、
[01-nested-mutate.R](bug-hunt-2026-10-23/01-nested-mutate.R)。

```r
d <- tibble::tibble(g = "a", x = 1)
summarize_with_margins(
  d,
  nested = list(summarize_with_margins(
    d, bit = grouping_bit(g), .grouping = rollup(g)
  )),
  .grouping = rollup(g)
)
```

内側を単独で実行したときの`bit`は`c(0L, 1L)`だった。
上記では外側の詳細行に入る内側結果が`c(0L, 0L)`、外側の合計行では
`c(1L, 1L)`になった。namespaceを明示しても、`grouping_id()`にしても再現した。
全く同じ内側呼び出しを関数に包むと正常になったため、実行時の共有状態よりも
構文の静的な探索範囲が原因と切り分けた。

普通のdplyr処理でも再現した。内側の`data.frame(g = 1, x = 2)`に対する
`mutate(inner, across(everything(), ~ .x * 2))`を外側のMargin summaryに直接
書くと、期待した`g = 2, x = 4`ではなく`g = 1, x = 4`になった。
外側のgrouping column除外が、内側の別データの選択に適用された。
内側の`share_of_total()`の誤拒否も同じ境界欠落の症状群に含めた。

原因箇所は`R/grouping-context.R`の`rewrite_grouping_expr()`と
`R/summary-selections.R`の`rewrite_summary_selections()` / `local_summary_selection()`。
内側の独立したdata maskを境界とせず、外側のplan・grouping set・group varsで
再帰していた。`R/utils.R`の`rewrite_evaluated_call_parts()`はlanguage captureの
境界を扱っていたが、このdata maskの所有者の切り替わりは表していなかった。

ADR 0019の静的な名前認識は確認したが、別のMargin operationのGrouping bitを
外側の値に変えることは正当化しなかった。修正には、各walkで独立した
data mask/capture所有者の境界を扱う必要がある。単に関数全体の走査を止めると、
それまで対応していた式まで失うので、既存のlanguage capture契約との照合が必要になる。

## 2. dtplyrの型付きメタデータが実入力を表していなかった

再現:
[02-dtplyr-factor.R](bug-hunt-2026-10-23/02-dtplyr-factor.R)、
[02-dtplyr-selection.R](bug-hunt-2026-10-23/02-dtplyr-selection.R)。

```r
x <- dtplyr::lazy_dt(tibble::tibble(f = factor("a"), v = 1L))
x <- dplyr::mutate(x, f = "z")
dplyr::collect(expand_with_margins(x, .grouping = rollup(f), .id = "set"))
```

`collect(x)$f`には`"z"`があったが、Margin結果の詳細行の`f`は`NA`になった。
4つのMargin verb、各sort、単一grouping setでも再現した。
これは**返却結果の誤値**であり、呼び出し元のテーブルを破壊したという主張ではない。

原因は`R/backend-metadata.R`の`dtplyr_metadata_safe_step()`が、root直後の
atomic scalar代入を無条件で安全と認め、ゼロ行rootで得た型を採用したことだった。
data.tableの既存列への代入は行数に依存した。

- factorへの新文字値代入では、2行以上の実データで新levelが追加されたが、
  ゼロ行proxyには追加されなかった。古いlevelsによるfactor復元が新値をNAにした。
- 1行入力ではscalar代入が列型を置き換えたが、ゼロ行proxyは元型を保持した。
  例えば`integer`列への文字値代入後、`where(is.numeric)`がその列を誤選択した。
- `.check_margin_label = TRUE`でも、新しいfactor値と同じlabelの衝突を
  見逃した。古いfactor metadataを信じて値の検査対象から外したためだった。

ADR 0020のdtplyrメタデータに関するamendmentは、忠実な型・levelsが得られない
derived stepを拒否する方針だった。読み取り許可を追加せずに修正するなら、
zero-row評価と実評価が一致するstepの判定を狭めるか、行を読まずに正しい
メタデータを導けることを示す必要がある。

## 3. Arrowの構築中に要求していないcollectが完了した

再現: [03-arrow-read.R](bug-hunt-2026-10-23/03-arrow-read.R)。

```r
x <- arrow::Table$create(tibble::tibble(.data = "x", b = "y"))
expand_with_margins(x, .grouping = grouping_set(".data", "b"))
```

利用者が`collect()`を呼ばず、単一grouping setを要求しただけでも、
構築中に自動`collect()`が1回実行され、戻り値1行を得てから
`object 'conversions' not found`で失敗した。traceはentryだけでなくexitの
`nrow(returnValue())`も記録した。

```text
automatic collect entries: 1
completed automatic collect row counts: 1
outcome: object 'conversions' not found
```

`R/margin-label.R`の`label_margin_branch()`が生成する複数列の`mutate()`で、
先行する`.data`列の上書きがArrowの評価maskに干渉した。後続変換が未対応処理と
扱われ、Arrowの吸収動作に入った。`R/grouping-adapter-union.R`の
`summarize_margin_branch()`にある吸収拒否handlerはordinary summaryだけを
保護し、その後のlabel変換とexpansionを保護していなかった。

上流Arrow単独でも同型のmask問題を確認したが、この再現では利用者のsummaryに
未対応処理がなく、marginplyr自身の生成コードが読取を起動していた。
したがってADR 0020の読取契約に対するmarginplyrの不具合として採用した。

範囲はTable、RecordBatch、それぞれからのqueryで、summaryとexpansionに再現した。
Datasetとそのqueryは読取0回で上流が拒否し、RecordBatchReaderは読取0回で
packageが拒否した。**外部DBやDatasetへの無許可読取を確認したものではない。**
dimensionの順を`grouping_set("b", ".data")`へ変えると、同じ入力を読まずに成功した。

## 4. branch結合で有効な列名が変わった

再現: [04-name-repair.R](bug-hunt-2026-10-23/04-name-repair.R)。

```r
x <- tibble::tibble(g = "a", sales...1 = 1L)
expand_with_margins(x, .grouping = rollup(g))
```

入力の`sales...1`が結果で`sales`になった。`New names:`という通知は出るが、
payloadやsummary outputの改名自体はエラーにならなかった。
dimensionの`g...1`、固定キー、`.id = "set...1"`では、後続処理が元の名前を
参照して`Element ... doesn't exist`で失敗した。ネストされたpayloadにも改名が残った。

`R/grouping-adapter-union.R`の`bind_margin_branches()`が使う
`dplyr::bind_rows()`のname repairが`...<number>`suffixを取り除いた。
後続のGrouping planやfactor metadataは元名を持ち続けていた。
禁止名の`...` / `..1`は根拠から除き、spreadsheet import等で生じる有効な名前だけで
再現を確定した。

432組合せで影響を確認した。data.frame・tibble・data.tableのeager入力で発生し、
dtplyrと単一branchの対照では発生しなかった。`.key`は結合後に導入されるため正常だった。
ADR 0016のclass/attribute委譲を踏まえても、元名での内部参照が壊れることは
委譲では説明できなかった。単純にローカル`union_all()`に置き換えるだけでも
name repairが起きるので、結合境界で名前の整合性を保つ必要がある。

## 5. SQL shareの固定キーがpronounとして解釈された

再現: [05-fixed-pronoun.R](bug-hunt-2026-10-23/05-fixed-pronoun.R)。

SQLiteのメモリDBに`.env = "fixed"`と`g = c("x", "y")`を持つtableを作り、
次を構築すると失敗した。

```r
summarize_with_margins(
  x, n = dplyr::n(), p = share_of_total(n),
  .by = dplyr::all_of(".env"), .grouping = rollup(g),
  .margin_label = NULL, .check_share_source = FALSE
)
```

診断は`Can't rename columns with .env`、`.env`が`rlang_ctxt_pronoun`であるという
ものだった。`.data`では`rlang_data_pronoun`になった。shareを外す対照は成功した。

`R/share.R`の`apply_joined_shares()`が、join keyの改名に
`rlang::syms(join_names)`を渡したため、列名がtidyselectのpronounになった。
SQLite・DuckDB・PostgreSQL × 2種類の名前 × Parent/Totalの12ケースで再現した。
試験プロセス内だけで当該箇所を文字列によるrenameへ変えると、12ケースとも
期待した比率`0.5, 0.5, 1`になった。実装ファイルは変更していない。

## 6. PostgreSQLのportable経路でtyped missingの型が失われた

再現: [06-postgres-null.R](bug-hunt-2026-10-23/06-postgres-null.R)。

```r
x <- dplyr::copy_to(con, tibble::tibble(g = 1L), temporary = TRUE)
expand_with_margins(
  x, .grouping = rollup(g), .margin_label = NULL, .id = "set"
) |> dplyr::collect()
```

`UNION types integer and text cannot be matched`で失敗した。生成SQLの主要部分は:

```sql
SELECT *, 1 AS "set" FROM input
UNION ALL
SELECT *, 2 AS "set"
FROM (SELECT NULL AS "g" FROM input) AS q
```

内側subqueryの未知型NULLがPostgreSQLでtextに確定した。
`NULL AS "g"`だけを`CAST(NULL AS INTEGER) AS "g"`に変えると成功し、
列順とidの型は変更不要だった。

`R/margin-label.R`の`label_margin_branch()`が未型付けNAを生成し、
後続のid投影等でsubqueryに包まれたことが原因だった。
`R/grouping-adapter-union.R`の`summarize_margin_branch()`が作る
Parent share用のprivate keyにも同じ未型付けNAがあった。

確認した範囲:

- logical・integer・double・Date・POSIXctの5型で再現。characterは成功。
- expansionは`.id`指定または`.sort = "last"`で再現。idなし・sortなしは成功。
- summaryは`.duplicates = "keep"`で選ばれるportable経路で再現。
  `.duplicates = "drop"`のnative経路は成功した。
- NULLとNA_character_ labelで再現。5型 × 3失敗形の15ケースは、
  NULLだけの型CASTで全て回復した。
- **デフォルトの文字labelでも**、portable Parent shareのprivate keyで再現した。
  Parent shareなし、Total shareだけ、native経路では成功した。

public typed-missing labelとParent shareの元型keyを、表示labelの型とは独立に
保持する必要がある。無許可の実データ読取で型を推測することはADR 0020に反するので、
修正はその制約を守る必要がある。

## 7. matrix/array sourceの拒否が内部計算まで遅れた

再現: [07-matrix-source.R](bug-hunt-2026-10-23/07-matrix-source.R)。

```r
x <- tibble::tibble(g = c("a", "b"), x = c(2, 6))
summarize_with_margins(
  x, v = crossprod(x), p = share_of_parent(v), .grouping = rollup(g)
)
```

ordinary matrix summaryは成功したが、share追加後は生成された`if_else()`で
`condition must be a logical vector, not a logical matrix`になった。
`marginplyr_error`ではなく内部の`dplyr:::mutate_error`が漏れた。
`v = sum(x^2)`というplain scalarの対照は期待比率`0.1, 0.9, 1`になった。

`R/share.R`の`check_share_scalar()`はlengthを、`is_share_source_type()`は
integer/double storageと`!is.object()`を調べた。しかしbase matrix/arrayは
length 1でもdimensionsを持ち、`is.object()`はFALSEだった。
後続の`apply_joined_shares()`の条件式にdimensionsが残って失敗した。

Parent/Total、`matrix(2)`、3D arrayで確認した。
これは**事前拒否と診断の欠陥**であり、誤った比率が返ったという報告ではない。
plain scalarに限定する契約を維持するならsource validatorで拒否すべきである。

## 8. ローカルworktreeがsource tarballに混入した

標準のsource buildと、テスト以外の`R CMD check`を実行した。

```r
rcmdcheck::rcmdcheck(
  path = ".", args = c("--no-tests", "--no-manual"),
  check_dir = "/tmp/marginplyr-bughunt-20261023/root/package-check",
  error_on = "never"
)
```

ビルド時のcheckoutには`.git/info/exclude`で無視された既存`.worktrees/`があった。
`.Rbuildignore`には対応する除外がなく、生成tarballの833 entriesのうち658 entries、
展開後8,703,992 bytesがその2つのcheckout由来だった。`.git`参照ファイルも
2件含まれていた。buildで長いpathの警告が出て、checkはhidden filesと
non-portable pathsの2 NOTEを出した。

Gitの無視設定はRのbuild除外として作用しなかった。
これは**そのディレクトリがあるローカル環境での除外漏れ**である。
clean commitをarchiveするReview-ready checkの成果物や、配布済み成果物への
混入を確認したものではない。今回のtarballはローカル検証だけに使用した。
[08-build-contents.R](bug-hunt-2026-10-23/08-build-contents.R)にtarballのpathを渡すと、
配下の混入がないことをassertする。今回のtarballでは658件を検出して失敗した。

### 採用しなかったもの・補足

- SQLite 3.53.3の`true` / `false`列名の一部失敗は裸SQLでも再現した。
  dbplyrの`.env` aggregate翻訳失敗もordinary summaryで再現した。
  package独自の問題とは数えなかった。
- empty Grand totalのordinary SUMにおけるSQL/ArrowのNULLとRの0の差、
  空のordinary aggregate列のR型、NaN/Infのbackend差は既存契約と照合して除外した。
- 3D array dimensionに非欠損labelを付けると、matrix専用の拒否を通り抜けて
  内部`as.character()`のsize errorになった。NULL labelなら動作した。
  arrayに関する明示的な公開保証が弱いため、確定7件には加えず、
  `R/margin-label.R`のmatrix限定guardを見直す際の補足に留めた。
- 空文字warningでは`Caused by`行がなく、保守的な診断parseがgroup contextを
  削除せず、複数報告になった。値の正しさには影響せず、診断の境界に関する補足とした。
- 他OS、他R/依存バージョン、PostgreSQL以外の外部DBサーバ、実データの巨大負荷、
  ネイティブSQL文実行中のOS割込み、CRAN remote incoming checkは今回未検証だった。
  全入力空間の無欠陥証明ではない。

3担当による探索に加え、別担当が7件をADRと照合して反証確認した。
