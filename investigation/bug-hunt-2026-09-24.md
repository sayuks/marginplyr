# Public-interface bug hunt

Investigated: 2026-09-24
Revised: 2026-09-24 — Publication triage split C10 and left C07's exemption scope open; see Revisions below.

Revision: `960b17c989ce789726ae404278da0c5582c3942d` (clean working tree
before the investigation). Package: marginplyr 0.1.0.

## Scope and result

This investigation exercised the exported Margin verbs, Grouping specification
constructors, inspection, contextual helpers, and Parent/Total shares through
their public interfaces. It compared observed results with the documented
contracts, ordinary dplyr, independently computed grouping results, and other
backends. No package implementation was changed and no GitHub issue was filed.

Twelve reproducible issue candidates were established. C01–C05 silently changed
values, grouping, or row counts; C06 made supported Arrow queries uncollectable;
C07 executed a lazy input before collection; C08 changed the result schema;
C09–C10 rejected valid calls. C11 required a stateful naming expression, and C12
concerned the diagnostic for a matrix dimension. Those last two had lower
practical priority than the ordinary data-processing cases.

The existing full testthat suite passed, including snapshots with
`NOT_CRAN=true`. Its successful result did not cover the new reproductions.

## Reproduce

From the repository root, with the dependencies listed below installed:

```sh

# Or select cases:
Rscript investigation/bug-hunt-2026-09-24.R C01 C02 C03
```

The [companion script](bug-hunt-2026-09-24.R) asserts the expected public
behavior. On the investigated revision it reported **12 of 12 checks failed**
and exited with status 1. This was an intentional red reproduction, not a
replacement for the package test suite. Each case included a successful
control or an explicit invariant. An eventual fix should turn its case green;
C05 and C11 also accepted a targeted Package condition as a valid remedy.

Environment: macOS, R 4.6.1 (2026-06-24), pkgload 1.5.3, testthat 3.3.2,
dplyr 1.2.1, dbplyr 2.6.0, tibble 3.3.1, vctrs 0.7.3, dtplyr 1.3.3,

The companion script's DuckDB connections used `shared_home = FALSE`; SQL

## Issue candidates

### C01 — Expand unnamed rewritten data-frame summaries before later summaries read them

Suggested priority: P2, first group to address because the result is silently
wrong. Affected: local summaries containing an unnamed data-frame-valued user
call with a rewritten helper, followed by another ordinary summary.

```r
x <- tibble::tibble(g = c("a", "a", "b"), x = 1:3, total = 100)
frame <- function(x) data.frame(total = sum(x[[1L]]))
summarize_with_margins(
  x, frame(dplyr::pick(x)), later = sum(total), .grouping = rollup(g)
)
# total: 3, 3, 6
# later: 200, 100, 300   (expected: 3, 3, 6)
```

Ordinary dplyr made the expanded `total` available immediately and produced
`later = 3, 3` for the detail groups. Without an input column named `total`,
the Margin call instead raised `object 'total' not found`. A later explicit
`total = 999` was also overwritten by the delayed expansion, yielding 3, 3, 6.

`name_rewritten_summary_dots()` in `R/summary-selections.R` assigned the
original expression's name before evaluation. dplyr therefore packed the
frame, leaving the old input in the data mask. `expand_assigned_data_frames()`
expanded it only after the branch's entire `summarise()` completed. The late
`mutate()` also explains the overwrite of a later output.

Contract: ADR 0028, *Expand a data-frame summary marginplyr named*, and the
public ordinary-summary semantics. Related completed work: #435 and #604.
Acceptance should cover both a missing and a same-named input column, later
direct reads/selections, and later overwrites; checking only final column names
would miss the value corruption.

### C02 — Keep typed grouping identity through nesting before converting display labels

Suggested priority: P2. Affected: both nesting verbs, local and dtplyr, with
non-missing character Margin labels.

```r
x <- tibble::tibble(g = c(1, 1 + 1e-15), value = 1:2)
nest_with_margins(x, .grouping = grouping_set(g))
# One outer group containing both rows; expected two one-row groups.
```

`summarize_with_margins(..., n = dplyr::n())` returned two detail groups on the
same input. `.margin_label = NULL` or using `g` as a fixed `.by` key preserved
both groups. With `.keep = TRUE`, the incorrectly merged cell still held the
two distinct original keys. A rollup returned two outer rows instead of three.

This also occurred for the two distinct instants in a repeated daylight-saving
hour: `2026-11-01 05:30:00 UTC` and `06:30:00 UTC`, displayed in
`America/New_York`. Both stringify to `2026-11-01 01:30:00` although one is
EDT and the other EST. It was therefore not limited to unusual floating-point
printing. All 36 tested combinations of data.frame/tibble/dtplyr, both nesting
verbs, both `.keep` values, and the three `.sort` values reproduced it.

`execute_margin_nest()` expanded and labelled the input first.
`label_margin_branch()` in `R/margin-label.R` converted included keys with
`as.character()`. `nest_expanded_margins()` in `R/nest_with_margins.R` then
grouped by those display values. Distinct original keys had already become
identical at that point.

Contract: the nesting reference promises a cell per group in each grouping
set; the summary reference's *Display labels and grouping identity* and
`CONTEXT.md` define a Margin label as display. Related but distinct from the
Parent-share typed-key fix in #600. Acceptance should retain original key
identity rather than merely increase numeric printing precision.

### C03 — Match partial across/if_any/if_all arguments before rewriting selections

Suggested priority: P2, first group to address because values change silently.

```r
x <- tibble::tibble(g = c("a", "b"), x = 1:2, y = 3:4)
summarize_with_margins(
  x, dplyr::across(.c = x, .fns = sum), .grouping = grouping_set(g)
)
# x: 2, 4; y: 4, 6
```

Ordinary dplyr matched `.c` to `.cols` and returned only `x = 1, 2`.
`parse_across_arguments()` in `R/summary-selections.R` matched argument names
exactly. It treated `.cols` as absent, inserted the default selection, and left
`.c = x` to be forwarded to `sum()` as an additional value. That changed both
the selected columns and the arithmetic. A related `if_any(.c = x,
.f = ~ .x > 0)` call succeeded in dplyr and failed under marginplyr.

The repository's Option-argument rule rejects abbreviated *values* of
marginplyr options; it does not make R argument matching inside ordinary
dplyr-compatible calls different. Acceptance should test `.c` and `.f` against
fully spelled equivalents, including selection rewrites and forwarded dots.

### C04 — Traverse evaluated call heads when searching and rewriting contextual helpers

Suggested priority: P2. Affected: summary expressions containing a statically
visible helper inside a computed function position.

```r
x <- tibble::tibble(g = c("a", "a", "b"), x = 1:3)
summarize_with_margins(
  x,
  out = (function(z) function(dummy) z)(
    ncol(dplyr::pick(dplyr::everything()))
  )(0),
  .grouping = rollup(g)
)
# out: 2, 2, 3; expected 1, 1, 1
```

The ordinary argument-position form `out = ncol(pick(everything()))` returned
1, 1, 1. Reading names instead of counts exposed `g,x` in the detail branches
and `g,x,..marginplyr_key_1` in the Grand total branch. Grouping columns and an
internal key escaped the selection boundary.

The same gap made `(if (grouping_bit(g) == 0) sum else length)(x)` raise the
helper's out-of-context error, and allowed the explicitly refused
`cur_group_id()` spelling to execute when placed in that `if` condition.

`map_call_parts()` and `searched_call_parts()` in `R/utils.R` descended into
arguments but not the evaluated call head. The alias-dependency walk already
handled that distinct subtree. This is not a request to resolve a dynamically
chosen helper name: the nested `pick()`, `grouping_bit()`, and `cur_group_id()`
calls were written explicitly and statically visible.

Contract: ADR 0019's reserved-helper rule and the public exclusion of every
fixed/variable grouping key from summary selections. Acceptance should cover
selection, grouping rewrite, and refusal scans over the same evaluated subtree,
while retaining the documented language-capture boundaries.

### C05 — Refuse row expansion that bypasses dtplyr share cardinality validation

Suggested priority: P2. Affected: dtplyr shares whose source expression is
scalar but another ordinary summary expands the same grouping row.

```r
x <- dtplyr::lazy_dt(tibble::tibble(g = c("a", "b"), v = c(2, 4)))
summarize_with_margins(
  x, z = sum(v), p = share_of_parent(z), extra = 1:2,
  .grouping = rollup(g)
) |> dplyr::collect()
# 10 rows; the same call without p has 6 rows.
```

Adding only Total share produced 12 rows; adding both helpers produced 20.
The Grouping plan still contained exactly two sets. `extra = unique(v)` also
reproduced the problem (ordinary 4 rows, Parent 6, Total 8), whereas a scalar
list-valued `extra = list(1:2)` did not. Bare dtplyr summarise produced its
ordinary multirow result without the extra multiplication.

`check_share_scalar()` in `R/share.R` inspected `sum(v)` before dtplyr recycled
it alongside `extra`. Denominator mapping then selected multiple rows per
key, and `apply_joined_shares()` performed a many-to-many match. A direct
non-scalar source was already rejected; this indirect route escaped that guard.

Contract: ADR 0010 says shares do not synthesize rows, and ADR 0017 transfers
the source/cardinality rules to Total shares. This candidate does **not** ask
for general multirow-summary support: local dplyr 1.2.1 rejected that ordinary
shape. A targeted refusal at dtplyr collection, before producing the multiplied
result, would satisfy the defect. Acceptance should test both helpers together
as well as independently.

### C06 — Preserve Arrow physical types when generating typed-missing Margin dimensions

Suggested priority: P2. Affected: summary and expansion on Arrow dimensions
whose physical type does not round-trip through the R prototype.

```r
x <- arrow::Table$create(
  g = arrow::Array$create(c(1L, 2L), type = arrow::int64())
)
summarize_with_margins(
  x, n = dplyr::n(), .grouping = rollup(g), .margin_label = NULL
) |> dplyr::collect()
# Invalid: UnionNode input schemas must all match ... g: int64 ... g: int32
```

The expected three rows could be collected from a manually constructed union
using `arrow::Scalar$create(NA_integer_, type = arrow::int64())`. The failure
also occurred with `NA_character_`, empty input, and `expand_with_margins()`.
A non-missing text label succeeded.

`grouping_selection_proxy()` in `R/backend-metadata.R` converted the Arrow
schema to a data frame. `margin_column_info()` retained its R prototypes,
and `label_margin_branch()` generated an R missing value from them. Reinjecting
that value inferred Arrow's default physical type, which differed from the
included branch's original type.

Measured failures included int8/int16/int64, uint8/uint32/uint64, float32,
decimal128, date64, timestamp(s/ms/ns), large_utf8, and time64. Measured
controls included int32, float64, date32, timestamp(us), utf8, and time32.
This was not an enumeration of every Arrow type.

Contract: the public typed-missing `.margin_label` behavior. The mismatch was
introduced by marginplyr rather than by an upstream conversion before the call.
Acceptance should execute both verbs with physical-type-sensitive fixtures and
preserve laziness while retaining those types.

### C07 — Avoid executing full dtplyr inputs while acquiring a zero-row selection proxy

Suggested priority: P2. Affected: immutable dtplyr steps with upstream
operations, including typed inspection.

```r
seen <- integer()
probe <- function(x) { seen <<- c(seen, length(x)); x }
x <- dtplyr::lazy_dt(tibble::tibble(g = c("a", "b", "c"), v = 1:3)) |>
  dplyr::mutate(v = probe(v))
y <- summarize_with_margins(x, n = dplyr::n(), .grouping = rollup(g))
seen
# 3, although y has not been collected
```

An ordinary uncollected `dplyr::summarise(x, n = n())` left `seen` empty.
`inspect_grouping(x, .grouping = rollup(where(is.character)))` likewise
executed the function on all three rows. A names-only inspection did not need
the typed proxy and was outside this reproduction.

`grouping_selection_proxy()` called `collect(head(.data, 0L))`. dtplyr rendered
this as `head(copy(`_DT1`)[, `:=`(v = probe(v))], n = 0L)`:
the zero-row limit applied after the full upstream operation. The test that
checked zero returned proxy rows did not establish that the input's operations
processed zero rows.

Contract: the `inspect_grouping()` reference's *Formats and ordinary tibble
behavior* promises a local plan without reading source rows. ADR 0020 exempts
the zero-row typed-metadata read, while stating that the lazy input's data
remains unread until requested. The demonstrated issue was the full-input
execution hidden behind that zero-row result. Heavy
calculations and user-function side effects could therefore occur before
collection. The isolated zero-row roots used for Mutable-step inspection
provided an existing comparison; no implementation change was made here.

### C08 — Retain SQLite typed-missing dimension types after share staging

Suggested priority: P2. Affected: all-missing variable dimensions with a typed
missing label, after either share helper.

```r
con <- DBI::dbConnect(RSQLite::SQLite(), ":memory:")
x <- dplyr::copy_to(con, tibble::tibble(g = NA_character_, v = 1), "probe")
summarize_with_margins(
  x, z = sum(v, na.rm = TRUE), p = share_of_total(z),
  .grouping = rollup(g), .margin_label = NULL, .check_share_source = FALSE
) |> dplyr::collect()
# g is logical; the ordinary result without p has character g.
DBI::dbDisconnect(con)
```

Character, integer, and double all-missing dimensions all became logical with
either Parent or Total share. Ratios and row counts stayed correct in this
minimal case. Additional tests of fixed `.by` keys retained their types; the
finding should not be generalized to those keys.

`sql_margin_type_anchor()` in `R/grouping-adapter-union.R` already protected
the ordinary result against SQLite's all-NULL type inference (#527). The
share join/projection in `R/share.R` surrounded that intermediate union and
lost the protection at the final result boundary. This was confirmed by placing
a zero-row source-column anchor before the exact final SQL: all six
type/helper combinations recovered their original types without changing the
summary or share values. No extra schema query was necessary in that control.

Contract: typed-missing labels retain the dimension type. The documented
SQLite share-source opt-out does not opt out of grouping-column types.
Acceptance should retain #527's ordinary coverage and add the later share
stage, respecting the no-unrequested-read and ordering contracts.

### C09 — Check across unpacked output names rather than the outer pack name

Suggested priority: P2. Affected: valid `.unpack` calls whose outer name matches
a grouping column or the requested `.id`.

```r
x <- tibble::tibble(g = c("a", "b"), x = 1:2)
summarize_with_margins(
  x,
  dplyr::across(x, ~ tibble::tibble(n = sum(.x)),
                .names = "out", .unpack = TRUE),
  .grouping = grouping_set(g), .id = "out"
)
# `.id` (`out`) conflicts with a summary output.
```

The output of across was `out_n`, not `out`; ordinary dplyr confirmed it.
Likewise `.names = "g"` with `.unpack = TRUE` should create `g_n`, but was
rejected as an overwrite of the grouping dimension. These were false
collisions, not requests to relax real output-name protection.

`known_across_output_names()` in `R/summary-selections.R` used the outer name
without incorporating `.unpack`. Acceptance should allow those noncolliding
outer names and still refuse the actual expanded name when it collides.

### C10 — Do not treat frame-constructor controls or shadowed bindings as definite output names

Suggested priority: P2. Affected: unnamed data-frame summaries and selected
ordinary constructor bindings.

```r
x <- tibble::tibble(g = c("a", "b"), x = 1:2)
summarize_with_margins(
  x, data.frame(x = sum(x), check.names = FALSE),
  .grouping = grouping_set(g), .id = "check.names"
)
# `.id` (`check.names`) conflicts with a summary output.
```

`check.names` was a `data.frame()` control and was not an output column.
Ordinary dplyr returned only `g` and `x`. A dimension itself named
`check.names` was falsely rejected in the same way.

`known_data_frame_output_names()` in `R/summary-selections.R` treated every
named argument except `.name_repair` as an output. A related overclaim applied
when a caller bound `tibble <- function(...) data.frame(z = 1)`: a call to
`tibble(foo = 1)` with `.id = "foo"` was refused even though the only output
was `z`. A shadowed `list()` used as across's function-list expression caused
the analogous false prediction of function names.

Contract: ADR 0019 explicitly makes the frame constructors ordinary lexical
lookups, not reserved Contextual helpers. These examples support one output-name
prediction audit, but frame controls and shadowed bindings could be split into
separate implementation tickets. Acceptance should test actual constructor
controls and preserve ordinary lookup without forcing unknown bindings merely
to guess an output name.

### C11 — Validate the names actually produced by the native summary build

Suggested priority: P2, lower practical priority because it requires stateful
naming. Affected: native DuckDB path, measured with dynamic glue in `.names`.

```r
calls <- 0L
nm <- function() {
  calls <<- calls + 1L
  if (calls <= 2L) "out" else "g"
}
# remote contains g = c("a", "b"), x = 1:2
summarize_with_margins(
  remote, dplyr::across(x, sum, .names = "{nm()}"),
  .grouping = rollup(g), .margin_label = NULL
) |> dplyr::collect()
# A single g column holding 1, 2, 3. The original keys and summary name are gone.
```

The name was evaluated three times: prediction, the separate
`native_summary_output_names()` build, and the real summary build in
`R/grouping-adapter-native.R`. The first two checks saw a harmless name; the
last build overwrote the grouping column and was not equivalently rechecked.
Its SQL was `SELECT SUM(x) AS g ... GROUP BY GROUPING SETS ((g), ())`.

The public contract refuses a summary that overwrites a grouping column. A
targeted error, or evaluating and retaining one authoritative naming result,
would both avoid this silent loss. The suggested issue should focus on actual
output validation rather than promise a particular evaluation count to callers.

### C12 — Report an actionable label refusal for matrix grouping dimensions

Suggested priority: P3. Affected: local matrix dimensions with the default
non-missing Margin label.

```r
x <- tibble::tibble(g = matrix(1:4, ncol = 2), v = 1:2)
summarize_with_margins(x, n = dplyr::n(), .grouping = rollup(g))
# Generated across/as.character call fails with dplyr_internal_error().
```

`.margin_label = NULL` succeeded. Matrix keys were named explicitly in the
Margin-order documentation, but `validate_margin_label()` in
`R/margin-label.R` recognized only data-frame columns as packed dimensions
that cannot take a non-missing label. The later `as.character()` flattened the
matrix into an incompatible length, exposing an internal backend invariant
through a package-generated expression.

Contract: ADR 0015 distinguishes actionable Package conditions from an internal
invariant failure. A targeted refusal analogous to the existing packed-frame
diagnostic would be sufficient; this finding does not require inventing a
display encoding for a matrix key.

## Breadth of validation and rejected signals

- Full existing suite: `Rscript -e 'Sys.setenv(NOT_CRAN="true");
  pkgload::load_all(quiet=TRUE); testthat::test_local(reporter="summary")'`.
  Terminal exit 0, `DONE`, no test failures/warnings/skips reported. All optional
  backends named in the environment were available.
- Local independent grouping/nesting oracle: 160 scenarios and 480 comparisons,
  using 16 key shapes, empty/populated data, optional fixed keys, and
  grouping_set/rollup/cube with typed-missing labels. All comparisons passed.
  Shapes included factors/ordered factors, date/time/duration, list, matrix,
  packed/zero-column frames, zero-column matrices, complex and raw keys.
- Grouping-plan expansion: 500 recursive specifications generated with seed
  607, checked against an independent oracle for included-set order, retained
  duplicate occurrences, fixed keys, Grouping bits, and Grouping identifiers.
  All comparisons passed.
- Backend type/empty-input grid: 960 public-verb calls (192 local references and
  768 comparisons) across local, dtplyr, Arrow, DuckDB and SQLite. It exercised
  eight source types, empty/populated data, two label policies, three plans,
  summary/expand, `.sort = "last"`, and `.id`. Twelve Arrow errors were instances
  of C06. Seventy-eight value/display differences reproduced in ordinary
  upstream collect/coercion controls and were excluded: logical/date/time
  conversion and a DuckDB integer64 ingestion problem already present after
  `copy_to()` without marginplyr.
- Native versus portable DuckDB: 26 aggregate-expression comparisons and 48
  calls over 12 upstream query shapes and two label policies. No new value
  mismatch was established. Unsupported paste expressions and dbplyr
  subquery-order warnings were external conditions, not issue candidates.
- Independent Parent/Total-share oracle: 100 fixed seeds, each with/without
  fixed partitions, for 200 calls. Missing keys, duplicate input rows, negative
  and zero values, and missing source values were included. All ratios matched.
- Cross-backend share differential: 15 fixed seeds × two fixed-key choices ×
  two label policies × four backends = 240 calls. All measured ratios agreed.
  Two schema mismatches led to C08; the ordinary SQLite result retained its
  type, so these were not dismissed as unavoidable upstream conversion.
- Additional share-key probes covered 12 key shapes, fixed/variable use and
  two label policies. The matrix default-label failure became C12; a packed
  data-frame default-label refusal was already documented and excluded.
- Both C05 and C08 were independently rerun by a second investigator, including
  upstream controls and the six SQLite final-anchor counterfactuals.

The GitHub open issue list was checked for duplicate reports. It contained the
CRAN release issue and two upstream-report tasks, none covering these
reproductions. Relevant closed tickets are cited above as related work, not
presented as unresolved tickets or as evidence that a fix had been applied here.

## Limits and disposition

This was a correctness hunt on the recorded revision and library versions,
not a proof that no further bugs exist. Live SQL execution used DuckDB and
SQLite; PostgreSQL and commercial SQL engines were not live-tested. Other R
versions, operating systems and dependency versions were not rerun. Website
rendering, release readiness, and CRAN submission were not part of this work.

The only repository additions were this dated note and its executable
reproductions. `investigation/` was excluded by `.Rbuildignore`; no package
source, generated documentation, package test, or dependency metadata changed.
The review-ready publication boundary was not invoked: there was no package
change or pull request to publish. The issue candidates remain proposals for
the user; none was posted to GitHub.

## Revisions (2026-09-24)

Publication triage retained the measured behavior above and qualified C07's
contract conclusion: ADR 0020 expressly exempts the metadata operation that
caused the full-input evaluation. Whether that exemption permits intermediate
full-source work, and what to do when faithful metadata cannot be obtained
without it, remained undecided. The C07 assertion records the stronger reading
of the no-source-row promise; it is not an approved implementation requirement.
[Issue #625](https://github.com/sayuks/marginplyr/issues/625) received
`needs-triage` for that decision.

C10 became two independently verifiable tickets: constructor-control parsing
and ordinary function-binding resolution. The original twelve cases therefore
produced thirteen issues. The other twelve tickets received `ready-for-agent`
because their expected behavior followed the existing contracts. Shared source
modules were not treated as blocking dependencies; every ticket recorded no
prerequisite issue.

index. Each issue carried its own acceptance criteria and immutable evidence
